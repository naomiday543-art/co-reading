── 一、結論 ────────────────────────────────
「選論文原文一段來問」與「選 AI 回覆一段來追問」現在是同一條骨架、兩種來源。
quote JSON 多 source／message_id；缺省＝論文原文。AI 回覆是 markdown、畫面字≠DB 字串，
所以 message 來源的偏移一律以純文字投影為準，前後端共用同一顆函式。後端照樣有硬閘門
（驗投影後的 slice===text，不合 400、零上游、不寫 DB）。paper 來源的行為、DB 裡的 JSON、
送給模型的字串逐字不變（工單 14 既有測試全綠）。

── 二、做了什麼 ────────────────────────────
2.1 src/markdownPlain.js（§2.2）零依賴純函式。脫標題／強調／刪除線／行內碼與圍欄標記
（內容保留）／清單前綴（縮排保留＝層級看得出來）／引言／連結只留文字／表格管線換兩空白；
分隔線與表格分隔列整行消失。換行與空白保留——段落形狀留著偏移才穩。兩個刻意設計：
① 冪等是構造上成立（行首標記「剝到不能再剝」的迴圈，不是剝一次）；
② 底線只在詞界脫，full_text／message_id 這種 snake_case 不會被咬掉。
frontend/src/lib/markdown-plain.js 直接 re-export 後端那一顆（§2.2 三條路選第一條）。
理由：兩份複製品漂一個字，後端 slice===text 就變隨機 400；與其釘兩份不漂，不如只有一份。
測試釘「兩個 import 路徑是同一個函式物件」。Vite root 是 frontend/、此 import 跨出 root，
npm run build 是這條線的驗收（已過）。

2.2 src/quote.js（§2.1／§2.3）
- parseQuote 認 source／message_id；source==='message' 沒有 message_id 一律當解不出來。
- validateQuote(sourceText, raw)：基準字串由呼叫端決定。message 來源對不上 →
  「選取內容與回答原文不一致」；超長 →「引用範圍超出回答長度」。其餘規則不變。
- renderQuotedMessage(quote, message, fullText, {turn}) 第二型前綴
  「【引用你先前的回答（第 N 輪）】」＋引言＋她的問題＋「（回答時先說明你先前那句話的
  意思與依據，再回應她的問題；若先前說錯了，直接承認並更正。）」
- buildQuoteContextBlock 的 message 分支：那則回答 ≤2,000 字整段給，超過退成選段前後各
  800 字（兩端補刪節號）；附她當時問的那句（≤300 字，超過截斷）。標【被引用回答的上下文】
  ＋【那一輪她問的是】。位置照舊在變動區最後。
- assistantTurnOf／assistantTurnMap：輪次＝第幾則 assistant（依 seq，1-based），前後端
  共用這一顆 ⇒ 畫面上的「第 3 輪」與 prompt 裡的「第 3 輪」保證同一個數字。
- quoteLogLabel → <source>:<chars>字（§2.4）。

2.3 src/routes/chat.js：message 來源先查那則訊息——不屬於這篇論文 → 400「找不到被引用的
回覆」；不是 assistant → 400「只能引用 AI 的回覆」（§2.5 的閘門）。四種 400 一律零上游、
一列都不寫。loadHistory 改成一次撈整串再依 beforeSeq 過濾（輪次要照整串數才跟前端一致，
被引用回答的全文與她當時的問題也要現查）。送出當輪與三個回放入口共用同一顆渲染 ⇒
同一輪回放幾次都逐字相同。

2.4 src/ai.js：脈絡來源 message 時吃 options.quote.sourceText（路由現查的投影），paper 時
照舊吃 paper.full_text。接的位置一個字沒動——變動區最後，穩定前綴不碰。

2.5 前端（§2.4）：ChatPanel 的 markdown 容器釘 data-cr-msg-id（偏移不釘在 DOM 上，那是
投影的事，DOM 只負責說「這是哪一則」）。訊息區 onMouseUp/onTouchEnd 抓選取，三個閘門：
兩端落在同一顆氣泡 → 那則是 assistant → 在投影裡唯一命中。引用卡／引用塊文案分兩型
（「引用原文 · 第 S–E 字」／「引用 AI 回答 · 第 N 輪」），連結字「跳回原文」／「跳回那則
回答」（後者走工單 18 的 messageJump＋cr-msg-flash）。placeholder 也分兩型。index.html 加
多次命中的中性提示藥丸 .cr-ask-selection[data-hint]，AI 氣泡 ::selection 比照文字版。

── 三、附錄 A：「多次命中就拒」是怎麼決定的（§2.2 二選一）──
工單給兩條路：①錨點法取離 anchor 最近的命中；②唯一命中才允許，否則請她多選幾個字。
選 ②（工單也指定 ②）。理由留在這裡，免得以後有人想「優化」成 ①：
- 錨點法在論文原文成立，是因為段落是我們自己排的、每段掛得住 data-cr-offset。AI 氣泡是
  ReactMarkdown 渲染的，DOM 結構隨 markdown 內容變（表格、清單、巢狀強調），釘不住錨點。
- 「離 anchor 最近」在 DOM 不受控時只是猜。猜錯的代價不是 400，是悄悄把別段餵給模型——
  正是工單 14 §3.1 立那道閘門要防的事。
- 拒絕的成本很低：她選 ≥8 字才彈按鈕，重複到那個長度的句子很少，多選幾個字通常就唯一。
實作仍留一層退讓：先照原樣 indexOf；找不到才把兩邊空白都壓成一格再找一次，偏移再映射回
投影。這是接住「DOM 把軟換行渲染成空白」「表格儲存格之間塞 tab」這類空白差異——字一樣，
只是空白形狀不同，那不該算對不上。唯一性判斷兩層都做，退讓不會變成「隨便挑一個」。
她會看到的四種反應：選不到 8 字 → 什麼都不彈（手滑不該跳按鈕）；唯一命中 →「問這段」；
命中不只一次 →「這段字在這則回覆裡出現不只一次，多選幾個字再試」（不是按鈕，點一下收掉）；
對不上投影 →「這段選取對不上回覆的原文，換個選法（避開表格邊界）再試」。

5. 點「跳回那則回答」→ cr-msg-flash 落在被引用那顆氣泡上，滾過去並閃一下。✅
6. 另種一則有重複句子的回覆，選中重複那段 → 浮出的是提示藥丸不是按鈕。✅

── 五、偏離工單之處（三條，都不大）──
1. paper 來源正規化後刻意不塞 source:'paper'。§2.1 說「parseQuote 正規化這兩欄」，§3 紅線
   又說「paper 來源與工單 14 逐字相同（既有測試全綠）」。既有測試有三處 deepEqual 直接比
   {text,start,end,page}，DB 存的 JSON 也是這形狀。相衝時以紅線為準：缺省就是缺省，來源
   一律由 quoteSource() 讀。⇒ 舊列不動、新的 paper 列也不變形，只有 message 多那兩欄。
2. 改了工單 14 測試裡的兩條斷言。§2.4 明講 [CHAT] start 的 quote= 要加來源，所以
   quote=97字 → quote=paper:97字、quoteLogLabel({start,end}) → 'paper:20字'。這是 §2.4 要求
   的結果，不是回歸；行為面（prompt／DB／HTTP）完全沒動。
3. 多了一個工單沒點名的常數 DEFAULT_REPLY_QUOTE_QUESTION＝「請說明你這段話的意思，以及
   你是根據論文裡的什麼這樣說的」。§2.3 只說了 message 型的指令句，沒說「只引用、沒打字」
   時替她問什麼；沿用 paper 那句（「它在全文裡的作用」）套在 AI 回覆上讀不通，所以補了一句
   對稱的。這句話她隨時可以改，改了不動任何邏輯。
另外兩個已知限制（不是偏離，是投影法天生的邊界，寫下來免得以後當 bug 查）：
- 跨表格邊界的選取可能對不上：selection.toString() 在儲存格之間給 tab／換行，投影給兩個
  空白。空白壓平那層接得住大部分情況，但選取剛好從表格中間起頭時仍可能落到提示那句。
- 被引用的回答被編輯／重生截掉之後輪次算不出來，前綴退成不帶輪次的【引用你先前的回答】
  （不是印 null）。這種情況下引用那則 user 本來也被一起截掉，實務碰不到；留著只是不讓它炸。
