## 1. 系統現況（給沒看過代碼的讀者）

### 1.1 是什麼

Co-Reading 是一個**本機**論文閱讀器：Express 5（ESM）後端 + React 19/Vite 前端 + better-sqlite3，可包成 Electron。使用者實際以 `npm run dev`（後端 :3456、Vite :5173）在瀏覽器用，**不用 Electron 殼**。公開倉：`github.com/naomiday543-art/co-reading`（MIT）。

### 1.2 資料流

```
PDF 上傳 → pdf-parse 抽全文 → AI 通讀（五段結構化摘要：背景/方法/結果/結論/局限）
        → 帶全文討論（SSE 串流，每輪帶整篇全文）
        → 手動點「提取洞察」→ insights 表（六維度）
跨論文：討論時以 FTS5 trigram 撈 3 條其他論文的相關洞察注入 prompt（被動）
```

### 1.3 關鍵檔案（先讀這些）

| 檔案 | 職責 | 本文相關位置 |
|---|---|---|
| `src/ai.js` | 所有 AI 請求、prompt 組裝、串流 | `chatAboutPaper()`（討論主鏈；跨論文注入在其中 `searchInsights(userMessage, { excludePaperId, limit: 3 })`）、`analyzePaper()`、`buildChatSystem()` |
| `src/memory.js` | 洞察提取 | `EXTRACT_PROMPT`（L7）、`TYPE_TO_DIMENSION`（L51）、progress 跳過（L199） |

## 2. 使用者回饋（原話，2026-09-10 組會後）

1. 「目前是不支持多个文献一起对比嘛，要先读一篇提取洞察之后再读另外一篇，那如果我需要有方法对比的话要怎么办呢？」
2. 「页面的文献还是有点小，看的时候不方便。我现在还是开的两个窗口，看到有问题才打开 coreading」
3. 「讨论的部分能够调整字体大小，现在有点太小了」
4. 「AI 通读完文章之后，就有点为这篇文章 defense 的感觉」
5. 「好像只能提取到洞察，而没有归类到别的分类诶？目前的分類機制是什麼？」→ 追問：「那是不是一開始設定引導的時候就應該加一個詢問 user 研究領域方面的？並且同一個 user 很有可能涉獵不同方面的」

第 2 條裡「看到有問題才打開」是重要的設計輸入：**她把 co-reading 當「有問題時的顧問」，不是主閱讀器**。

## 3. 診斷

### 3.1 閱讀空間太小（回饋 2）

- 現象：她開原生 PDF 閱讀器＋co-reading 兩個視窗。
- 代碼：`PaperDetail.jsx` 左（摘要／全文 tab）右（聊天）兩欄，`split` 百分比可拖，但永遠平分注意力。
- 根因：介面預設「看論文」和「聊論文」同等重要，與她的實際用法（讀為主、問為輔）不符。

### 3.2 討論區字太小（回饋 3）

- 代碼：`.prose-chat` 無獨立字級，跟 `body 14px`。
- 根因：沒做，純缺功能。

### 3.3 無法多篇對比（回饋 1）

- 現況：一篇論文一個聊天室；`chatAboutPaper()` 只帶當前論文全文；跨論文只靠 FTS 被動撈 3 條洞察。
- 不能帶多篇全文：單篇 45k–147k 字，兩篇疊起來十幾萬 token，慢且貴。
- 可用資源：每篇都有五段結構化摘要，`summary_methods` 96–519 字，正是「方法對比」的料。
- 六維度裡的「**共振**」（兩篇呼應／打架）、「**闪回**」（讀這篇想起那篇）本來就是跨論文位置，一直沒入口。

### 3.4 導師替論文辯護（回饋 4）

- 代碼：`SPEC.md` 討論 prompt 五條回答要求＝「基於論文內容回答／論文沒有就說沒有／講清楚／引用具體段落／用她的語言」。**五條全是轉述者姿態，沒有一條給 AI 審稿人位置。** `feat/constitution` 的憲章好一點（價值觀 2「保留矛盾」），但只講「論文 vs 她的洞察」「兩篇論文互打」，**沒說這篇論文本身可被質疑**。
- 機制：她問「作者為什麼選血清？跟人體內不一樣」→ AI 的任務被定義成「去論文裡找作者的理由並解釋」→ 圓場。她的問題是質疑，它回的是辯護。
- 細節：「不要編造論文中沒有的信息」（防幻覺，正確）與「不要評估」被綁在一起——「作者的血清模型跟體內循環差很遠」不是編造，是評估，prompt 沒給這個空間。
- **邊界（她追問「AI 不了解科研現狀怎麼看出明顯局限」後補的）**：AI 的訓練資料有截止日且不完整，「這方法過時了」「已被反駁」這類判斷只能是印象。所以批判必須有據，分三檔：
  (a) 能從論文本身推出的局限才主動指出——證據→結論的跨度、作者自寫的局限被放在最後、對照／樣本／統計通則、測的≠聲稱的、前後矛盾；
  (b) 需要領域現狀的判斷**只能引她自己的洞察庫**（讀第十篇時前九篇就是「現狀」），不得從訓練資料編；
  (c) 真要用訓練印象，必須標明「這是我的印象，可能過時」。

### 3.5 六維度只有兩個有自動通路（回饋 5）

- 代碼：`EXTRACT_PROMPT` 只認 fact／hypothesis／progress；`TYPE_TO_DIMENSION = { fact:'概念', hypothesis:'悬题' }`；progress 不入庫只 log。**延伸／你的研究／闪回／共振零自動路徑。** 註解寫了「hypothesis → 你的研究（if about user's own project）」但代碼沒實作。
- 歷史原因：三 type 照 research-gateway 契約對齊；六維度是 co-reading UI 層；兩套沒對上。
- **根因：AI 不知道使用者是誰、研究什麼**（憲章／設定／提取 prompt 都沒有）。「延伸」定義是「跟你的題目連上」、「你的研究」是「關於你自己的項目」——沒有題目就判不了。
- 她的追問把形狀改了：**「延伸」的定義本身就是跨方向**（讀 A 方向想到 B 方向），所以「一個研究領域欄位」不夠，要**多方向、每個帶描述**。
- 順帶 bug：提取不去重——13 條裡兩條各出現 3 次（多按幾次「提取」就多提幾次）。

## 4. 方案

### 4.0 地基：研究方向 × 知識樹合流（§3.4、§3.5 的前置）

**主張**：知識樹一直沒人用（純資料夾，放進去不會發生任何事），研究方向沒地方放——兩者合成一件事：

- **頂層節點＝研究方向**，每個節點加一段描述（`description` 欄：這個方向在做什麼、關心什麼問題）。可多個。
- **論文上傳時問「這篇屬於哪個方向」**（可跳過；跳過就不掛）。
- **AI 讀得到**：討論 system prompt 與提取 prompt 注入「這篇屬於 X 方向（描述…）；她另有 Y、Z 方向（描述…）」。
- **引導兩時機**：首次打開問「你目前在做哪幾個方向？」（各一句話）；設定頁可增改。

一次解決三件事：知識樹有了存在理由；研究方向有了家；「延伸」「你的研究」有了判斷依據。

Schema：`tree_nodes` 加 `description TEXT`（migration，idempotent，照 `src/db.js` 既有慣例）。**樹結構仍 100% 歸 co-reading**；出海到 gateway 時只以 `tree:<path>` tag 帶方向名，不帶描述（契約不變）。

### 4.1 閱讀模式（§3.1）

- 一鍵：左欄撐滿（PDF／全文）、sidebar 收、聊天縮成右下浮動按鈕；點開＝蓋在 PDF 上的抽屜（寬度可拖），問完關掉繼續讀。
- 狀態存 localStorage，跨論文保持。
- 純前端，動 `PaperDetail.jsx` + `ChatPanel.jsx` 容器。

### 4.2 聊天字級（§3.2）

- 小／中／大三檔（14/16/18px），`.prose-chat` 與輸入框同步，存 localStorage。
- 可併進 4.1 同一張工單。

### 4.3 多篇摘要對比（§3.3）

- Library 多選 2–4 篇 → 「對比」→ 後端 `POST /api/compare`：拿各篇標題＋五段摘要（**不帶全文**）→ AI 吐「維度 × 論文」對比表（背景／方法／結果／結論／局限）＋一段分析（相同、相異、打架處）。
- 結果可一鍵存成洞察，維度預設「**共振**」，`source_paper_id` 存主篇、`tags_json` 帶其餘論文 id。
- 誠實限制：只能比到摘要抓到的層次。要實驗參數級（「A 用 120 nm、B 用 50 nm」）得另做「按章節抽全文段落」（`section_progress` 表 0 筆可用來做），列為進階、另開單。

### 4.4 憲章：不當辯護人（§3.4）

在 `src/prompts/CONSTITUTION.md` 價值觀加一條，並改回答結構：

> **你不是這篇論文的辯護人。** 作者的每個選擇都可以被質疑。她提出質疑時，先判斷她的質疑成不成立，再說作者的理由。論文有能從文本本身推出的明顯局限（證據與結論的跨度、作者自承但輕描淡寫的局限、對照／樣本／統計、測的與聲稱的不一致、前後矛盾）而她沒問，主動指出。
> **批判要有據**：需要領域現狀的判斷只從她的洞察區塊引用；沒有洞察可引就標明「這是我的印象，可能過時」，不得把訓練印象當事實。
> 回答分兩層：先「論文說的」（準確轉述、引出處），後「我的評估」（明確標記）。

實作位置：`feat/constitution` 分支（先 rebase main，落後 7）。改文字不碰代碼；補測試釘「質疑型問題的回答含『我的評估』段」。

### 4.5 提取：六維度直出＋去重（§3.5）

- `EXTRACT_PROMPT` 改為直接輸出 `{type, dimension, content}`：`type` 仍三值（gateway 契約不變），`dimension` 六值由模型依「使用者研究方向區塊」判斷；`TYPE_TO_DIMENSION` 退為 fallback。
- 「延伸」「你的研究」的判斷依據＝4.0 注入的方向描述；「闪回」「共振」提取時帶入該篇既有的 FTS 相關洞察（現有 `findRelatedInsights`）讓模型判斷。
- 去重：提取時把該篇已有洞察的 content 一併給模型並要求「不要重複已存在的」，落庫前再做 normalized-content hash 擋一次。
- 依賴 4.0。

## 5. 優先序與依賴

```
4.1 閱讀模式 ──┐
4.2 字級   ────┤ 獨立，可先做（體驗，半天＋半小時）
               │
4.0 方向×樹 ───┬──→ 4.4 憲章（需先 rebase/合併 feat/constitution）
               └──→ 4.5 提取六維度＋去重
4.3 對比 ── 獨立於 4.0，但「共振」存法受 4.5 影響；摘要品質是它的天花板
```

建議批次：

| 批次 | 內容 | 量級 | 為什麼這個順序 |
|---|---|---|---|
| 一 | 4.1 + 4.2 | 半天＋半小時 | 每天都撞，零依賴，先解決日常痛 |
| 二 | 合併 `feat/constitution` → 4.0 → 4.4 | 1–2 天 | 地基；三個「認識使用者」的問題共同前置 |
| 三 | 4.5 | 1 天 | 依賴 4.0 的方向描述 |
| 四 | 4.3 | 1 天 | 讀到一定量才用；「共振」存法等 4.5 定 |

## 6. 明確不做

- 不帶多篇全文進 context（成本／延遲不可接受）
- 不把樹結構或方向描述複製進 research-gateway（契約：只收 `tree:` tag）
- 不改 gateway 契約的三 `type`
- 不動摘要／視覺 prompt、不裝 poppler、不改 preset `vision_mode`（§1.6）
- 不做「全庫 RAG 問答」——那是另一個產品，先用摘要對比滿足「方法對比」

## 8. 給外部審閱者（Codex 等）的具體問題

請針對這幾條給意見，其他部分讀完有想法也歡迎：

1. **4.0 的做法**：把研究方向做成知識樹頂層節點（加 `description`），vs 獨立一張 `research_profiles` 表再讓樹節點引用它——哪個更乾淨？考量：樹已存在、論文已有 `tree_node_id`、gateway 契約只收 `tree:` tag。
2. **4.4 憲章措辭**：上面那段條文會不會讓模型過度批判？「回答分兩層」在串流輸出裡怎麼標記最不礙眼（Markdown 小標？固定前綴？）？
3. **4.5 去重策略**：提取時帶已有洞察讓模型自己避重（貴、每次都帶）vs 落庫前 hash／相似度擋（便宜、可能漏語義重複）vs 兩者都做——你會怎麼配？
4. **4.5 六維度直出**：讓模型一次判 `type` 和 `dimension` 兩個欄位，還是先判 `type` 再用第二個便宜請求判 `dimension`？考量：現在提取走 `deepseek-v4-pro`，結構化輸出穩定但慢。
5. **4.3 context 策略**：五段摘要（現案）vs 摘要＋每篇「方法」章節原文（用 `section_progress` 定位）——後者對「實驗參數級對比」有多大幫助，值不值得第一版就做？
6. **批次順序**：你會調整 §5 的順序嗎？特別是 4.3 要不要提前到批次二（她組會剛講完，對比需求可能馬上來）。
